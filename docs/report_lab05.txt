Крок 2. Прокоментувати бенчмарк та графік прискорення:
- Заміри проведено на процесорі Intel Core i5-13400 (10 ядер, 16 потоків), 32 ГБ RAM, 43 книги (65 МБ).
- Threads у Python 3.12: 1 воркер = 21.82 s, 16 воркерів = 23.50 s (speedup 0.93x, тобто сповільнення). Пояснення: через GIL байткод виконується лише одним ядром, а перемикання контексту кожні 5 мс створює накладні витрати.

- Закон Амдала: злиття merge займає ~0.8-1.0 секунди (~15% часу) і виконується послідовно в одному процесі, що обмежує максимальне теоретичне прискорення.
- Free-threaded Python 3.13t (PEP 703): де GIL вимкнено (sys._is_gil_enabled() == False), потоки масштабуються з 5.52 s до 2.40 s (speedup 2.30x) без копіювання пам'яті між процесами.

3. ГЛОСАРІЙ КЛЮЧОВИХ ТЕРМІНІВ:
• Global Interpreter Lock (GIL) — глобальний м'ютекс CPython, що дозволяє виконувати байткод Python лише одному системному потоку одночасно задля захисту лічильників посилань reference counts.
• CPU-bound навантаження — операції, обмежені швидкістю процесора (токенізація, хешування, розрахунок TF-IDF). Потоки не дають прискорення при наявності GIL.
• I/O-bound навантаження — операції, що очікують вводу-виводу (диск, мережа). Системні виклики I/O звільняють GIL, тому потоки дають прискорення.
• Шаблон Map-Reduce — розділення вхідних даних на неперетинні частини (Map: build_partial), паралельна обробка та фінальне об'єднання результатів (Reduce: merge).
• Закон Амдала (Amdahl's law) — закон, що обмежує максимальне прискорення паралельної програми: S_max = 1 / (1 - p), де p — частка паралельного коду. Послідовне злиття merge є вузьким місцем.
• Податок на серіалізацію (Pickling Tax) — витрати часу та пам'яті на перетворення об'єктів у байти при передачі між процесами через міжпроцесні канали зв'язку IPC.
• Free-threaded Python (PEP 703) — збірка CPython 3.13+ без GIL, де потоки виконують байткод одночасно на різних ядрах процесора завдяки оптимізованому immortalization та mimalloc.
• Гонка даних (Race condition) — помилка паралельного програмування, коли результат залежить від непередбачуваного порядку доступу потоків до спільної мутабельної пам'яті.

4. ВІДПОВІДІ НА REFLECTION (EXPLAIN AT THE WHITEBOARD):
Q1: Що таке GIL, що він блокує і навіщо CPython? Що він НЕ захищає?
A: GIL (Global Interpreter Lock) — це м'ютекс, який повинен захопити будь-який потік перед виконанням байткоду CPython. Він потрібен CPython через керування пам'яттю на лічильниках посилань (reference counting): якби потоки одночасно змінювали ob_refcnt без блокування, виникали б гонки даних і витоки пам'яті/звалювання. GIL захищає внутрішні структури інтерпретатора, але НЕ захищає інваріанти програми розробника. Наприклад, операція counter += 1 розгортається у кілька інструкцій байткоду, і перемикання потоків посередині втрачає інкремент.

Q2: Чому 8 потоків працювали не швидше за 1 потік? Що робили ці 8 потоків?
A: Тільки один потік виконував байткод CPython у кожен момент часу. Інші 7 потоків спали в очікуванні звільнення GIL операційною системою. Кожні 5 мс (sys.getswitchinterval()) працюючий потік примусово просять віддати GIL, ядра ОС перемикають контекст, деградує L1/L2 кеш процесора. Потоки просто стояли в черзі до одного ресурсу, тому час навіть збільшився з 21.82 s до 23.39 s.

Q3: Чому для процесів wall time склав ~7 с, а сумарний CPU time ~22 с? Куди пішли процесорні секунди?
A: У режимі ProcessPoolExecutor ядра процесора працювали паралельно. За 7 секунд реального настінного часу (wall time) кілька ядер встигли виконати загалом ~22 процесорні секунди роботи (сума по всіх процесах). Додаткові секунди витрачаються на створення процесів, імпорт бібліотек у кожному дочірньому інтерпретаторі та серіалізацію/десеріалізацію постінгів через pipe.

Q4: Чому функція для ProcessPoolExecutor має бути на рівні модуля? Що буде з lambda?
A: Дочірній процес у CPython під Windows використовує spawn: він запускає чистий інтерпретатор і імпортує модуль заново. Щоб викликати передану функцію, pickle серіалізує її за глобальним ім'ям 'findex.index.build_partial'. Анонімні лямбда-функції та локальні внутрішні функції не мають глобального кваліфікованого імені, тому pickle кидає AttributeError або PicklingError: Can't pickle local object.

Q5: Різниця між fork та spawn, небезпека fork і навіщо if __name__ == '__main__'?
A: fork (Linux) копіює стан пам'яті батьківського процесу (copy-on-write). Його небезпека: він копіює стан блокувань потоків, через що дочірній процес може назавжди заблокуватися в дедлоку, якщо потік батька тримав м'ютекс. spawn (Windows/macOS і default для Python 3.14) запускає новий інтерпретатор і імпортує вхідний файл заново. Без блоку if __name__ == '__main__' кожен дочірній процес при імпорті знову запустив би створення ProcessPoolExecutor, спричинивши нескінченний рекурсивний форк-бомбінг.

Q6: Закон Амдала. Злиття займає 15% часу — яке максимальне прискорення при N -> нескінченність?
A: Формула: S = 1 / ((1 - p) + p / N), де p — частка коду, що паралелізується (85%), а (1 - p) — послідовна частка (15%). При N -> нескінченність член p / N прямує до нуля, тому максимальне прискорення S_max = 1 / 0.15 = 6.67x. Навіть із тисячею ядер послідовний крок merge не дозволить прискорити програму більше ніж у 6.67 раза.

Q7: Чому вільний від GIL Python 3.13t виявляє баги, які стандартний приховував?
A: У стандартному Python GIL створює випадкову штучну серіалізацію: потоки рідко перемикаються всередині одного короткого методу словника чи списку. На Python 3.13t потоки фізично одночасно звертаються до пам'яті. Будь-який спільний лічильник чи список без Lock гарантовано ламається race condition, тому що у 3.13t більше немає глобального м'ютекса, який випадково прикривав помилки розробника.

Q8: Байткод counter += 1 (dis). Де втрачається інкремент?
A:
  1 LOAD_GLOBAL (counter)
  2 LOAD_CONST (1)
  3 BINARY_OP (+)
  4 STORE_GLOBAL (counter)
Якщо потік А виконав LOAD_GLOBAL (прочитав 10) і перемкнувся, потік Б виконує всі 4 інструкції і записує 11. Потім повертається потік А, додає 1 до прочитаного 10 і теж записує 11. Результат — дві операції дали 11 замість 12.

Q9: Приклади задач для Threads, Processes та Asyncio:
A:
1) Потоки (Threads) — I/O-bound завдання з блокуючим API (наприклад, фонове читання або збереження файлів на диск, запити через requests).
2) Процеси (Processes) — CPU-bound завдання на чистих обчисленнях Python (індексація тексту, парсинг, розрахунок матриць).
3) Асинхронність (Asyncio, Лаб 6) — десятки тисяч одночасних мережевих з'єднань з короткими повідомленнями (веб-краулер, чат-сервер, веб-сокет API), де потоки витрачають забагато пам'яті на стеки.
